One control plane.
Many nodes.

GPU nodes call home to the NAS. The controller decides what is healthy. LiteLLM routes inference. Caddy is the single Tailscale-facing door.

One contract, any fleet size

One Spark

A single-node runtime owns its endpoint and artifacts. The agent calls agents.vonk-forge.lan:8443; the controller publishes one route after fresh health evidence.

Two Sparks

A tensor-parallel gang has one entrypoint and one worker rank on the direct fabric. Both stable spk_… identities must acknowledge the same run before mia-deepseek-v4-flash appears.

Many Sparks

The planner places independent workloads and gangs across compatible nodes. Each gang can use an accepted subset; every other Spark remains available for different work.

There is no fixed fleet size, and an IP address is not identity. Client inference always follows Tailscale → Caddy → LiteLLM → one accepted entrypoint. GPU nodes never receive Tailscale OAuth, database, signing, or client API keys. LiteLLM never discovers containers; it uses only routes published from authenticated agent evidence.

Catalog resolution before execution

Identity layers

A model group contains models; a model version fixes upstream revision, format, artifacts, checksums, lineage and license; a recipe binds that exact version to a harness, runtime distribution, optional patch, topology, resources and interfaces. Read the model catalog operator guide.

Immutable resolution

Every reference resolves by kind, publisher, slug and content SHA-256. The controller admits a build only after the checked-in documents, source bundle, Fleet capacity and topology agree. Updates create new resolved revisions; rollback selects a prior exact revision rather than moving a tag or downgrading the database.

The setup, in eight steps

1

The NAS gets a stable name

The Compose installation uses a reserved NAS address and local DNS. The agent endpoint is something stable such as agents.vonk-forge.lan:8443.

No mDNS, no subnet scan, no guessing which machine is the controller.
2

Each GPU node is paired once

vonk-agent pair stores the controller URL and CA, creates the key on the GPU node, and exchanges an approved pairing code for its node certificate.

Spark → agents.vonk-forge.lan → Caddy's agent-only SNI → controller
3

The agents call home

Every Rust agent initiates outbound mTLS long polls. It reports inventory and claims only jobs for its certificate-bound node ID. The NAS never discovers or routinely SSHes into GPU nodes.

agent: “I am spk_…; inventory X; give me my next fenced operation.”
4

The controller chooses placement

A local recipe declares the artifacts, runtime, alias, port, resources and topology. PostgreSQL contains current installations, reservations and workloads. The planner decides which GPU node or gang can run it.

recipe + inventory + reservations → exact node/rank plan
5

Agents start and prove the workload

The assigned agents install and start the exact container revision. They return the observed endpoint and health evidence. For a gang, every rank must agree before anything is exposed.

spk_1 reports model API 192.168.20.41:8000; spk_2 reports worker ready
6

The controller publishes the route

It verifies node identity, management CIDR, recipe-declared port, model identity, freshness and health. Then it atomically generates LiteLLM's alias-to-endpoint configuration.

mia-deepseek-v4-flash → runtime-local alias → accepted Spark entrypoint
7

Requests enter through one door

A remote client reaches Caddy through Tailscale. Caddy sends /v1/* to LiteLLM. LiteLLM authenticates the key, resolves the alias, and calls the approved GPU node endpoint directly over the management LAN.

client → Tailscale → Caddy → LiteLLM → GPU node head model API
8

Bad health withdraws the route

If evidence becomes stale, a rank fails, or a recipe run stops, the controller removes the LiteLLM route before cleanup. Caddy does not invent a fallback, LiteLLM does not rediscover the container, and Hermes is available only while an accepted v1 run owns the exact hermes-agent alias.

health lost → alias withdrawn → stop/repair/rollback

Interface-specific publication

OpenAI serving

An accepted openai recipe publishes an alias through Caddy and LiteLLM to exactly one healthy endpoint-owner rank. LiteLLM receives only controller-authored, lease-bound routes; it never resolves catalog documents or discovers a container.

Artifact jobs

Image, video, audio, 3D and other artifact-producing jobs use their declared controller job and result APIs directly. Their progress and output artifacts do not become LiteLLM model aliases, while install, health, stop and cleanup still follow the same harness lifecycle. See execution harness operations.

Who knows what?

Caddy

Knows URL paths and security boundaries. It always sends /v1/* to LiteLLM. It knows no recipes, placements or model containers.

LiteLLM

Knows only the controller-published model aliases, healthy upstream URLs, API keys, quotas and replica policy.

Controller

Knows recipes, nodes, installation state, resources, topology, desired deployments and validated health evidence.

Rust agent

Knows its own node, local artifacts, containers, current operation fence and observed endpoint health. It does not choose fleet placement.

Model service

Knows how to serve inference. It does not connect to Caddy, publish itself, read the catalog or decide its public alias.

Do GPU node services connect to Caddy?

No. The agent calls the controller through Caddy's separate mTLS backend. Inference flows in the other direction: LiteLLM calls the validated entrypoint model service directly.

How does LiteLLM know what exists?

Only through the controller. A recipe says what should exist; authenticated agent evidence proves what actually exists. Both must agree before the route is published.
