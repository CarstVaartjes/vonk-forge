# Issue 598: automatic bounded failure evidence

Repository implementation on `codex/issue-598-20260908`, based on `fb2626a0`.
This is repository and disposable Linux evidence; no live NAS/Spark acceptance is claimed.

## Integrated behavior

- `FailureEvidenceService(sessions, clock=...)` is in `vonk_control.failure_evidence`.
  API and worker service factories instantiate it and schedule `.tick()` alongside other
  background services. It reads durable failed/waiting agent attempts, shared Jobs
  (including RecipeOperation, RunSwitch and artifact jobs), model-cache operations,
  and FleetProfileApplication. Fleet applications reuse their authoritative provider
  projection, including Library placement and preparation identities.
- `.tick(limit=32)` has a 250 ms admission budget, at most 32 rows per family,
  rotating family priority, and persistent timestamp/ID/attempt cursors. A single
  database transaction cannot be forcibly interrupted by this admission budget.
  Cursor retention is independent of bundle deletion, preventing repeated capture
  of historical failures after restart or expiry. Collector errors are isolated in
  `last_collection_error`; they never replace an operation result.
- `.decorate(operation_item)` adds existing `OperationEvidenceDownload` and
  `OperationEvidenceProvenance` to the result for the **exact current attempt**.
  Shared operation list/detail and job child-operation projections use this decoration.
- `install_failure_evidence_routes(app, actor_dependency=..., service=...)` in
  `failure_evidence_api.py` installs authenticated `getOperationEvidence` at
  `GET /api/operations/{operation_id}/evidence?attempt=N` (attempt required).
  The operation ID uses the same role policy as operation detail. Generated
  OpenAPI and clients include the typed bundle. Activity and `vonkctl operations
  evidence` download the exact attempt. Returned JSON has a content hash ETag,
  attachment disposition, no-store and nosniff headers.
- `failure_evidence_models` is registered with startup and Alembic metadata.
  Migration `0024_failure_evidence`
  creates only the two current tables; there is no old-data conversion or reader.
- **Result persistence hook**: validate and call `sanitize_diagnostics(raw)` on the
  optional nested diagnostics before persistence. Temporarily remove diagnostics
  from the receipt passed to the existing generic depth/8 KiB sanitizer; attach the
  validated sanitized typed document afterward. Running the generic sanitizer over
  diagnostics destroys its nested property lists and truncation metadata.
- `AgentFailureResult.diagnostics` and `RecipeJobRunResult.diagnostics` now both use
  exported `FailureDiagnostics`. Rust matches through
  `vonk_agent_protocol::failure_evidence::FailureDiagnostics`. The Rust executor
  attaches diagnostics only on failure before writing the durable terminal result.
  Preserve the dedicated job result shape; do not impose generic `status` and
  `error_code` on a failed job result. Validate that a failed `recipe.job.run.v1`
  result has nonzero `exit_code`. Contextual result validation and API admission
  enforce this for the actual authenticated agent endpoint.
- The `_typed_result_string` exception is deliberately restricted to the two typed
  log text leaves and declared diagnostic property values. Filesystem strings are
  inert observations there; generic path and command checks remain in force.
- Shared fixture: `agent_protocol/src/vonk_agent_protocol/vectors/failure-diagnostics-v1.json`.
  A valid job failure fixture is the existing `recipe-job-run-result-v1.json`
  envelope with `state="failed"`, `result.exit_code=1`,
  `result.reason="runtime failed"`, and `result.diagnostics` set to that fixture.
  Protocol tests exercise canonical serialization and typed read-back.

## Bounds and collection behavior

- Typed diagnostics: 16 KiB UTF-8 serialized total; each log keeps the final
  2048 input bytes and 32 lines, with explicit truncation/loss metadata. Unknown
  prior process-ring loss is `null`, not a fabricated count.
- Final bundle: 32 KiB, content hash checked and Pydantic validated on read.
  The receipt uses the existing nested `OperationFailureEvidence` model. Fleet
  context includes at most 128 node identities with an explicit omitted count.
  Unavailable or corrupted diagnostics never hide the primary operation failure.
- Default retention: 14 days, 2000 bundles, 64 MiB; bounded configurable values.
  Retention removes bundle content without deleting operation results or cursors.
- Agent reads only fixed `/proc` properties, free space for its data root, fixed
  `systemctl show` properties and `podman --version`. No network, environment dump,
  recursive directory scan, or SSH is used. Subprocess output is limited to 8192
  bytes using a nonblocking pipe; the systemd deadline is 150 ms and the shared
  final subprocess deadline is 200 ms. Timeout kills/reaps the collector child.
- Kernel restrictions and effective systemd properties are recorded separately.
  Missing observations have stable collector error codes. Actual Podman build
  and import failure outputs flow from the bounded process runner to sanitized
  tails before raw output is discarded. Other operations retain their structured
  failure receipt and bounded local observations. No unavailable logs, rank,
  preflight result, runtime version, or storage reading is invented.
- Controller collection uses already persisted observations; offline nodes cause
  no extra probe. Preflight properties are accepted in the canonical diagnostics
  extension; existing collectors do not independently execute a preflight probe.
- Producers redact secret lines, signed URL credentials/query values, opaque
  credential-like strings, and control-character obfuscation. Controller repeats
  redaction before blob persistence. Display can reapply its normal redaction.
